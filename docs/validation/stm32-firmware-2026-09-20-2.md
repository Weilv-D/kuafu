# STM32 Firmware Logic Review — 2026-09-20 (second review)

This record documents an independent fourth-pass review of the firmware,
layered on the 2026-09-13 / 09-16 / 09-20 records (all re-verified as
baseline before this pass started). Unlike the earlier 09-20 three-pass
review, this pass re-derived the architecture and every module from the
source alone — the prior records were read only afterwards, to check that
every documented invariant still holds and that no earlier fix regressed.

It is a software record: no hardware was flashed or driven.

## Scope and method

1. **Architecture pass** — module partition, the mode/phase/supervisor
   state machines and their interlocking gates, scheduler deadline
   structure (1 kHz fusion + telemetry on the DRDY tick, 250 Hz control on
   the wall clock, 50 Hz retry-on-busy legs, 4 ms wheel bus slots, 6 ms
   servo poll), peripheral bring-up order (DMA clocks and NVIC before the
   UARTs, DRDY armed before discovery, IWDG window vs. the blocking
   bench-calibration paths), and every ISR/main-loop concurrency contract
   (DDSM queue cursors, ST3215 deferred error application, Pi TX queue,
   ring producer reconstruction ordering).
2. **Detail pass** — walked scenario by scenario: cold boot, INIT→STAND
   arming, gate-open/gate-close dispatch under every mode, supervisor
   demotion and re-issue, transient-fault recovery, link loss/regain,
   servo-bus congestion, DMA restart, lost TX-complete interrupts, IMU
   init failure, tick wrap, and both bench calibration builds. Boundary
   conditions (ring index `size`, NDTR reload sample, queue overflow,
   uint16 saturating counters, float→int casts) and parser resynchronization
   paths were re-derived from the code.

## Defects found and fixed

### 1. (Medium-high) Gate-closed dispatch on enabled wheels left the last current-loop torque latched in the motors

**Files:** `Core/Src/main.c` (dispatch policy), regression in
`tests/test_ddsm315.c`.

The DDSM315 current loop holds its last setpoint. The dispatch layer sent
explicit zero-torque frames in `FAULT` — the 09-20 review's own record
states the rationale ("a read-only query would leave the last torque
latched in the motor") — but sent plain read queries in every other
gate-closed state. Those states are reachable with the wheels still
physically enabled: the plausible one is an actuator-supervisor HOLDING
demotion while the mode stays operational (e.g. the 100 ms leg-hold TX
window expires under servo-bus congestion, or leg feedback/posture goes
stale, while STAND/ACTIVE continues). In that window the motor keeps
driving the pre-closure LQR torque with no live control, and the backstop
is only the TILT fault at 45° after the robot has effectively fallen; the
wheels actively accelerate the fall and the robot can travel (the "爆冲"
failure shape). The exposure is bounded (roughly the 1 s servo-freshness
budget plus fall time) but it is exactly the window in which a
self-balancing robot must not be actively driven.

**Fix:** the dispatch now sends an explicit zero-torque frame whenever the
gate is closed and the wheel remains enabled (`wheel_enable_mask != 0`),
in any mode; plain queries are reserved for motors that are (or may be)
disabled — INIT/discovery and the disable-drain window, where a command
frame is pointless and the mode re-assertion sequencer owns re-arming.
Torque command frames elicit the same status reply as a query in this
driver (`expect_reply` derives from the frame type), so wheel feedback
freshness is identical in every branch — the property the query branch
existed to preserve. A zero-torque frame sent while a motor has reverted
to its velocity loop decodes as a zero *speed* command, which is the safe
value there too.

**Regression:** `test_ddsm315.c` pins the zero-torque frame encoding
(byte-exact, CRC over 9) and that a zero-torque transaction keeps the
reply/freshness channel (`expect_reply`, feedback restores online health).

### 2. (Low) Stale `SERVO_FAIL_LIMIT` comment claimed a fatal-FAULT path that does not exist

**File:** `Core/Src/main.c`.

The macro's comment said "Max consecutive servo failures before a fatal
FAULT lockdown". The macro is only the round-robin poll's `offline_after`
(device_health online state); fault latching is the safety layer's
freshness path. The comment described behavior removed long ago and could
mislead a reader into thinking a poll counter can lock the machine.

**Fix:** comment now states the actual role and points at the safety-layer
path. No behavior change.

## Documented observations (no code change)

Deliberate design decisions or accepted limitations, recorded so they are
no longer "undocumented behaviour":

- **Telemetry is silent while the IMU path is down.** The telemetry slots
  live inside the `g_system_ticks` block gated on `g_imu.initialized`. If
  the BMI088 dies (I2C dead while DRDY alive, or DRDY itself stopped), the
  Pi receives nothing at all — including FAULT frames — although the 250 Hz
  control section keeps detecting and latching faults on the wall clock.
  Diagnosis in that state is SWD-only. Moving telemetry out of the fusion
  block was considered and rejected for this pass: it cannot help when DRDY
  itself is dead, and duplicating senders adds a new interleaving for a
  narrow failure class that boot forensics already covers.
- **The DDSM115 feedback mode byte is diagnostic-only.** A wheel motor that
  power-cycles spontaneously reverts to its default loop while the firmware
  still believes it is in current mode; the recovery path is the pitch
  fault, not mode verification. Runtime verification (feedback mode vs.
  `DDSM_MODE_CURRENT`) was considered and deferred: no field evidence of a
  single-motor brownout exists, and a new fault source without a reproduced
  failure contradicts the repository's evidence-driven methodology.
- **The LQR position estimate freezes while the gate is closed.**
  `last_lqr_ms` advances only when the LQR actually runs, so a gate-closed
  period reintegrates at most one 20 ms step (`LQR_ELAPSED_DT_MAX`); odometry
  distance during the outage is not accumulated (worst case ~4 cm of
  `x_est` bias for a 100 ms demotion). Retained: splitting estimation from
  control inside `lqr_update_elapsed_dt` for a second-order position error
  is not worth destabilizing a field-validated controller.

## Independent re-verification (second pass, same day)

A second review pass re-derived the audit **without consulting the prior
review records or `docs/HANDOFF.md`** (they were read only afterwards, to
cross-check conclusions). Scope extended to everything the first pass had
not personally traced:

- **Machine verification of the physics→control→codegen chain** on the
  review host: `verify_physics_source.py` (28/28), `verify_controller_golden.py`
  (PASS), `generate_artifacts.py --check` (header byte-identical to the
  generator), 65 training/teleop/contract pytests, plus the balance-trace
  offline suite. The LQR/LQI sign chain, five-bar IK/FK closure, D0 gates,
  and generated constants are therefore verified by execution, not by
  reading.
- **Toolchain-level facts re-proven from the project files**: linker image
  ends at `0x2001FFBF` (`.uvprojx` IRAM/IRAM2 + map RW_IRAM2), so the
  64-byte RAM-top forensic area (`0x2001FFC0..0x2001FFFF`) cannot be
  allocated; stack is 4096 B against a measured ~0.8 KB deepest main-loop
  frame; `HSE_VALUE=8 MHz` matches `PLLM=8`; `TICK_INT_PRIORITY=0`.
- **Cross-layer byte-order audit** (firmware encoder ↔ Pi decoder ↔ contract):
  action field order `[dtau_common, dtau_yaw, dQx_L, dD0_L, dQx_R, dD0_R]`,
  telemetry joint order and per-field scales (wheel torque ×10000, speeds
  ×1000), hip observation assembly `[A_l, B_l, A_r, B_r]` in `serial_node`,
  and the dwell-relative FK sign chain (`fivebar_fk_relative`, `-left[1]`
  → positive D0). All consistent.
- **Quantization margins**: every int16 telemetry field checked against its
  physical range; only the gyro channel saturates above 32.767 rad/s
  (cosmetic; validity/freshness unaffected).
- **Arming-window edge of the zero-torque dispatch fix, re-derived**:
  enable/mode frames are no-reply transactions that hold the bus until
  their 12 ms quiet deadline, and the dispatch layer requires an idle bus,
  so at most ONE zero-torque frame can slip to a not-yet-enabled wheel per
  arming sequence — one health timeout, `consecutive_failures = 1 < 3`,
  no offline, no freshness effect. Confirmed benign.
- **Late-DDSM-reply edge**: a reply arriving after the transaction deadline
  can close the *next* transaction with a ≤12 ms-old genuine frame
  (same motor, CRC-valid) — inherent to request/response RS485 with
  timeouts, bounded, accepted.
- **Behaviours reviewed and accepted as deliberate** (noted here so they
  are documented decisions): a validated HELLO snaps the cached D0 back to
  the 58 mm dwell (safest crouch on a new Pi session; servo speed limits
  the slew); `teleop_single`/`link_probe` latch FAULT (ESTOP) on exit and
  on gamepad loss — no operator present means stopped; a CLIMB request
  from STAND is ignored (CLIMB is only reachable from ACTIVE; staying in
  STAND is the conservative response).

**Result of the independent pass: no new defects.** The first-pass fix was
re-derived as correct and necessary from the code alone, and the items the
first pass had taken on documented trust were either proven (linker, stack,
HAL config, sign chains) or shown benign with bounded worst cases.
