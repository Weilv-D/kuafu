# STM32 Firmware Logic Review — 2026-09-20 (fourth record)

This record documents an independent sixth-pass, whole-repository review of
the firmware and the Pi5 runtime. Per the task framing the review started
from the source alone: the architecture and every module were re-derived —
scheduler structure, state machines, driver concurrency contracts, bus
timing, and the cross-layer protocol — before any prior record or changelog
entry was consulted. The five earlier records were read only afterwards, to
cross-check conclusions; nothing in them was found stale.

It is a software record: no hardware was flashed or driven.

## Scope and method

1. **Architecture pass** — module partition (drivers / buses / health,
   safety machine, startup manager, actuator supervisor, runtime intents,
   control section, trace), the mode/phase/supervisor state machines and
   their interlocking gates, the four-layer deadline structure (1 kHz
   DRDY-gated fusion, 250 Hz wall-clock control, 50 Hz retry-on-busy legs,
   4 ms wheel slots + 6 ms servo poll), peripheral bring-up order, and
   every ISR/main-loop concurrency contract.
2. **Detail pass** — boundary conditions (ring index `size`, NDTR reload
   samples, queue overflow, saturating counters, float→int casts, fusion-dt
   and elapsed-dt clamps), parser resynchronization, fault entry/recovery/
   re-issue, gate dispatch under every mode, both bench calibration builds,
   tick wrap, and the IWDG budget against every blocking path (including
   the 370 ms bench ID-calibration block against the 1 s window).
3. **Contract pass** — `pi_link`/`pi_transport` against the Pi-side
   `protocol.py`/`serial_node.py`/`teleop_single.py`/`runtime.py`
   (framing, CRC coverage, sequence gates, D0 dynamic-gate mirror,
   heartbeat/action validation ranges, health payload layout, joint wire
   order vs Actor order), the encoder non-finite guards, and the
   workspace-solvability of every IK input the scheduler can produce.

## Defects found and fixed

Three findings, all closed in this round with regressions. Severity is
ranked by worst-case consequence on the running robot.

### 1. (Medium) The firmware receive sequence gate had no peer-restart resync — a corrupted HELLO locked a rebooted Pi out for the length of the previous session

**Files:** `Core/Src/pi_link.c` (`pi_link_parse_packet`), regression in
`tests/test_pi_link.c`.

The Pi-side `StreamDecoder` gained an 8-frame resync on 2026-09-16 for the
mirror-image failure (STM32 reboot restarts its TX counter at 0 and the
monotonic gate blackholes every CRC-valid frame until the counter climbs
back past the stored high-water mark). The firmware's own receive gate had
no such mirror. Every Pi-side program (`teleop_single`, `serial_node`,
`link_probe`) sends HELLO exactly once at startup, and a validated HELLO is
the only thing that resets the firmware's gate — so the lockout is reachable
whenever that single HELLO frame is corrupted on the wire (unplug noise, a
Pi reboot mid-line-break, baud-glitch during reconnect). Consequence: a
rebooted Pi's heartbeats — sequences restarting at 0 against a stored
high-water mark of an entire previous session — are sequence-gated until
the counter climbs back, which at the 50 Hz command rate is minutes; the
robot stays locked out of `ACTIVE` (STAND balance continues by design)
until the STM32 is power-cycled.

**Fix:** the exact mirror of the Pi-side rule. Eight consecutive frames
that are CRC-valid, non-HELLO, and rejected by the sequence gate alone
clear the gate baseline, and the next frame is accepted as the start of a
new session. Payload-invalid frames never count (line noise cannot open the
gate), and any accepted frame clears the streak, so isolated duplicates are
still dropped. The reject counter is packed into the existing
`have_rx_sequence` state byte (bit0 = baseline present, bits1..4 = streak)
rather than added as a new global, so the RW image — and with it the SWD
debug-script address contract — is unchanged by this state.

**Regression:** a session accepted at sequence 30000, then reboot-session
frames 0..7 all rejected, frame 8 accepted with its heartbeat applied, and
an isolated duplicate still dropped afterwards.

### 2. (Low) `ddsm_build_torque`/`ddsm_build_speed` reached an undefined float→int cast on a non-finite command

**Files:** `Core/Src/ddsm315.c`, regression in `tests/test_ddsm315.c`.

A NaN compares false against every clamp bound, so a non-finite torque
reached `(int16_t)(torque * DDSM_TORQUE_TO_RAW)` — undefined behaviour in
C. Unreachable through the current call chain (the LQR path validates
finiteness upstream: a non-finite pitch latches FAULT in the same control
deadline that would have dispatched it), but the builders are public
encoders, the same latent-trap class the repository already guards
(`quantize_i16`, `bmi088_read_temp`). A non-finite command now encodes as
zero torque (coast), never as a saturated command; +Inf, which previously
clamped to maximum torque, also decodes as zero — the safe reading of a
nonsensical request.

### 3. (Low) `servo_angle_to_tick` reached the same undefined cast on a non-finite angle

**Files:** `Core/Src/servo_mapping.c`, regression in
`tests/test_servo_mapping.c`.

IK outputs are finite by construction (`acosf`/`atan2f`), so the cast was
unreachable today; the guard exists for future callers of the public
mapper. The safe sentinel is the calibrated dwell tick — never a mechanical
extreme (0/4095), which a clamp would command.

## Reviewed and kept (bounded residuals and deliberate decisions)

Derived end-to-end this pass and either proven correct or accepted with a
bounded worst case; recorded so the next review does not re-litigate
without new evidence.

- **A late TX-complete can race a newly started DDSM transaction.** The
  12 ms no-reply deadline treats a missing TX-complete as completion and
  starts the next frame; if the "lost" interrupt was merely delayed beyond
  12 ms (≥11 ms of interrupt latency — an extreme environment), it can
  complete the *new* frame early. Worst case: one frame lost plus one
  spurious health failure on the wrong target; the bus self-heals on the
  next deadline. Requires an interrupt storm severe enough that the IWDG
  and stall forensics are already the relevant story. Not worth per-frame
  completion tokens.
- **ST3215 torque-enable frames are fire-and-forget** (the Feetech WRITE
  instruction elicits no reply), so "servo enable verified" is software
  truth: a lost enable frame leaves one joint torque-free while feedback
  (which is independent of torque) stays fresh. Mitigations: every
  FAULT→recovery cycle physically re-issues the enables, and the pitch
  proxy `leg_posture_safe` plus the 45° TILT backstop bound the
  consequence. Reading register 40 back to verify was considered and
  deferred — no field evidence of a lost enable exists, and it would
  change the poll format (evidence-driven methodology).
- **`Error_Handler` under a running IWDG is a reset loop.** The blink
  loop cannot outlive the ~1 s watchdog window, so a config-fatal state
  presents as periodic reset cycling rather than a steady blink. That is
  the intended self-recovery posture for bring-up failures (clock/UART
  init), and the reset cause is readable in the health telemetry.
- Re-derived clean, among others: the boot→INIT→STAND arming chain and the
  supervisor's observed-low latch under every entry path; the
  FAULT-gated enable sequencer; the grace-window suppression
  (device-driven only); the masked DDSM timeout re-validation; the ST3215
  echo filter against real query/reply byte sequences including the
  legit-prefix reply; ring/transport lap accounting across re-arm in both
  directions; the wheel-dispatch alternation and its sent-torque
  bookkeeping (the post-flip polarity is correct); the zero-torque
  gate-closed policy including the one-frame arming edge; LQR/LQI clamps,
  anti-windup, airborne leaky bucket, and the speed brake; Mahony
  per-channel validity and the gyro-only bound; the IK workspace proof
  for every reachable (qx, d0) input pair; the IWDG budget; and the
  cross-layer field order `[wheel_L, wheel_R, A_l, A_r, B_l, B_r]` ↔
  Actor order `[A_l, B_l, A_r, B_r]`.
